# Elite-Deep — инструкции для AI-агентов

## Команды

| Действие | Команда |
|----------|---------|
| Установка | `npm install` |
| Dev-сервер | `npm run dev` |
| Сборка одного файла | `npm run build` → `dist/index.html` |
| Юнит-тесты | `npm test` (650) |
| E2E | `npm run e2e` (63 проверки, headless Chrome) |
| Симуляция экономики | `node scripts/economy-sim.mjs [прыжков]` |
| Всё сразу | `npm run check` (тесты + сборка + e2e) |

На Windows вызывай Node по полному пути managed-рантайма:
`C:\Users\alexa\.workbuddy-ai\binaries\node\versions\22.22.2-2\node.exe`.

## Структура

```

├── main.js          # единственный файл, знающий обо всех остальных
├── logic/           # чистая логика, ноль импортов three
│   ├── rng.js       # mulberry32, hash2, rand01, int, pick, chance, shuffle, noise1, noise3, fbm3, ridged3
│   ├── galaxy.js    # генерация 64 систем, MST-граф маршрутов, JUMP_REFERENCE
│   ├── economy.js   # 19 товаров, computeMarket
│   ├── player.js    # ранг, инвентарь, рейтинг
│   ├── factions.js  # правительства, экономики, опасность, враждебность
│   ├── combat.js    # урон, перегрев, перезарядка, щиты
│   ├── reputation.js # репутация, розыск, память мира, слухи
│   └── missions.js  # контракты: генерация доски, принятие, выполнение, провал
├── sim/             # мост между логикой и three
│   ├── models.js    # геометрия кораблей, станции, астероидов; PBR-материалы, обводка с затуханием, пламя двигателя
│   ├── environment.js # процедурная equirect-проба: непрямой свет для PBR-материалов

│   ├── dust.js      # космическая пыль вокруг корабля: чувство скорости
│   ├── sky.js       # процедурное небо: звёзды, галактический пояс, туманности, пыль (instanced)
│   ├── world.js     # сборка сцены системы, трафик, стыковка, прицеливание
│   ├── flight.js    # состояние полёта — без единого импорта
│   └── render.js    # рендерер, камера, пост-обработка; хост неба
├── core/            # ввод и звук: не three и не игровая логика

│   └── audio.js     # процедурный синтез
└── ui/
    ├── hud.js       # Canvas 2D HUD
    └── station.js   # DOM-экраны станции

tests/               # node:test, зеркалит src/
scripts/e2e.mjs      # puppeteer, гоняет настоящую игру через window.__ELITE_GAME__
docs/                # CONTEXT.md, DECISIONS.md
e2e-shots/           # скриншоты, перезаписываются при каждом прогоне e2e
```

## Конвенции

- **Логика без three.** Всё в `src/logic/` — чистые функции без импортов
  рендера. Это делает модули тестируемыми в изоляции и детерминированными.
- **`flight.js` намеренно без импортов.** Состояние полёта — обычные объектные
  литералы. Границу с объектами three держит `render.js` (см. `toQuaternion`).
  Не «улучшай» это, заменив `flight.quat` на `THREE.Quaternion`.
- **Нос всех кораблей — локальный +Z.** Камера смотрит в −Z. Это закреплено
  тестами в `models.js`, `flight.js`, `world.js`, `hud.js`. Не меняй.
- **Цвета — только через `getHexString()`.** three r152+ конвертирует
  hex-литералы из sRGB в линейное пространство, поэтому `.r/.g/.b` — не те
  байты, что в исходнике. Сравнение напрямую молча ломается.
- **Генерируемые документы:** заголовки обычным регистром (никакого КАПСА),
  шрифт Calibri 11. Times New Roman и Arial запрещены.
- **Коммиты** — прямо в `main`, без feature-веток, ≤72 символов в заголовке,
  повелительное наклонение. Только когда пользователь явно попросит.

## Подводные камни

- **Один шаг ЛЦГ — не хеш.** Выбор из четырёх вариантов через
  `s = (s*1664525 + 1013904223) >>> 0` с последующим делением кластеризуется:
  для последовательных семян из четырёх типов достигались **два**. Если нужно
  разложить значение по корзинам — бери `mulberry32` или `hash2` из `rng.js`,
  они написаны ровно для этого.
- **Метрика «похожести» цвета не может быть суммой каналов.** Тест, суммировавший
  RGB, объявил серый и синий камни одинаковыми: у них совпала яркость при
  совершенно разных оттенках. Для различимости — евклидово расстояние в RGB.
- **Проверяй, что разброс меньше зазора.** У камней есть разброс оттенка внутри
  породы и зазор между породами. Инвариант: первый должен быть **уже** второго,
  иначе камень одной породы выглядит как камень другой. Тест на это поймал
  гранит и лёд, разошедшиеся на 0.0164 при разбросе 0.0171.

- **Камера смотрит по своей локальной −Z, а нос корабля — +Z.** Если отдать
  камере кватернион корабля как есть, она будет смотреть в **хвост**, и
  корабль полетит спиной вперёд относительно всего на экране. Именно это и
  было: замер — после отстыковки станция впереди на 376 юнитах, две секунды
  газа — 799. Лечится доворотом на пол-оборота **внутри системы корабля**
  (`quat * CAMERA_FLIP`), а не вокруг мировой оси: вокруг мировой горизонт
  завалится при тангаже. И помни, что HUD проектирует по носу — если камера
  смотрит не туда, рамка цели и трассеры окажутся в невидимой части кадра.
- **Проверяй, куда летит корабль, а не только куда он смотрит.** Ни один
  юнит-тест не видел этой ошибки: `faceToward`, `checkDocking` и вся логика
  работают с носом и остаются корректными. Поймал только пробник, который
  открыл газ и сравнил дистанцию до станции до и после.
- **Прежде чем «улучшать» эффект, измерь, где он находится.** Выхлоп рождался
  в 3–17 юнитах от объектива. Любая настройка размера давала либо невидимое,
  либо 55–97 % кадра; вопрос был не в настройке, а в геометрии. Иногда
  правильный ответ — удалить.

- **«Предпочитать интересное» — не бесплатное улучшение.** Генератор
  контрактов сначала *предпочитал* цель в кризисе, и доска вышла сплошь
  «emergency». Причина не в частоте кризисов (20 % систем), а в том, что
  кризис — единственное, что заставляет систему хотеть товар, который она
  обычно не потребляет: для скота и медикаментов пул нуждающихся был **весь**
  из кризисных систем. Если метка описывает большую часть списка, она не
  описывает ничего. **Юнит-тесты этого не видели** — каждый отдельный
  контракт был корректен; ошибка видна только на скриншоте доски.
- **Проверяй, что контент выводится, а не выдумывается.** Доска контрактов не
  содержит ни одного написанного задания: система предлагает отвезти то, что
  сама производит, туда, где этого нет. Всё нужное (`profile.produces`,
  `consumes`, `lacking`, `condition.demand`, `dangerOf`, память мира) уже
  существовало — контракт оказался *взглядом* на связанные данные, а не новой
  системой.

- **Проверяй, что функция-аргумент получает то, что ты думаешь.** Слух при
  входе в систему печатался числом `76`, потому что подборщик строк был
  написан как `(i) => name.charCodeAt(i % name.length)` — он получает
  **массив строк**, игнорирует его и возвращает код символа. Выглядит как
  правдоподобный хеш. Тест «слух — это строка» был бы зелёным и на числе;
  ловит только `lines.includes(result)`.
- **Написанное ≠ подключённое.** `reputation.js` содержал 202 строки рабочей
  механики — цены от репутации, восемь приветствий, враждебность патрулей,
  память мира — и **ни одна функция не вызывалась**. Проверяй не наличие
  кода, а наличие вызывающих: `grep -c "REP.standingPriceFactor" src/`.
- **Условие может быть верным и всё равно недостижимым — из-за квоты.**
  Блок зачисток в `generateBoard` был написан правильно и стоял последним с
  проверкой `if (offers.length < boardSize)`. Проверка корректна. Но цикл
  доставок выше заполнял все три слота всякий раз, когда система производила
  три вещи, нужные соседям, — и это случалось в 210 досках из 320. Замер:
  **0 контрактов на зачистку на 320 досок**, то есть один из четырёх типов
  контрактов не существовал. Спрашивай не «может ли условие быть истинным», а
  «может ли оно быть истинным **в этой точке потока**». Лечится резервированием
  ресурса заранее, а не правкой условия.
- **Объект, положенный в сцену напрямую, не уезжает вместе с группой.**
  `enterSystem` меняет группу системы целиком, но корабли трафика и четыре
  источника света добавлялись прямо в сцену рендерера. Замер: **104
  замороженных корабля после двенадцати прыжков** при десяти в текущей системе,
  и 21 направленный свет после двадцати — звезда покинутой системы продолжала
  освещать новую. Оба уродства стояли ровно там, где положено быть трафику и
  свету, поэтому не бросались в глаза. Заменяя подсистему, обойди **всё**, что
  она добавила, и спроси, где именно это лежит.
- **Проверка, которую видно только на длинном прогоне, стоит отдельного
  раздела e2e.** Обе утечки выше нашёл новый раздел, который вызывает
  `enterSystem` десятки раз. Прежние 51 проверка делали один прыжок: одна
  утечка на один прыжок укладывается в бюджет «меньше 200 объектов» и выглядит
  здоровьем.
- **Стенд может породить «баг», который ты собрался чинить.** Первый замер
  охвата дал 48° → 165° и выглядел как победа. Причина была в стенде: `spawn`
  задаёт кораблю скорость вдоль **старого** носа, и она рассасывается примерно
  за секунду — ровно столько, сколько длился замер. Обнулив скорость, я получил
  74° против 76°, то есть ничего, и откатил весь код. **Прежде чем радоваться
  «до/после», убедись, что оба прогона начинаются из одинакового чистого
  состояния:** поле, оставленное конструктором, легко перевешивает короткий
  замер.
- **Проверяй, можно ли вообще сделать то, что собираешься.** Охват не работает
  не из-за неудачной реализации, а из-за модели движения: скорость следует за
  носом, а выстрел требует носа в пределах 10° от цели. Лететь по флангу и
  целиться одновременно нельзя — замер по границе ввода в бой дал 2 выстрела
  за 30 с на 200 юнитах и **0** на 300. Прежде чем строить механику, спроси,
  допускает ли её существующая физика.
- **Тест, который проверяет только «не сработало», проходит и на сломанном
  намертво.** Тест границы огня утверждает обе стороны: за границей не
  стреляют **и** внутри стреляют. Без второй половины он был бы зелёным на
  пушке, которая не стреляет никогда.
- **Визуальное утверждение проверяется по отрендеренным пикселям, а не по
  значениям материала.** Были верные `roughness`, `metalness` и корректное
  затухание обводки — и проволочный шар в кадре. Замер по пикселям самого
  объекта (кадр с ним минус кадр без него): средняя яркость **18**, **89 %
  пикселей темнее 35**. Правильный вопрос не «материал описан верно», а
  «сколько света реально приходит в пиксель».
- **Правило, применённое не ко всем объектам, выглядит как работающее.** У
  корпусов `envMapIntensity` 1.35, у станции 1.5, у камней — 0.5. Замер с
  выключенной пробой окружения: камень падает с 14.4 до 1.2, то есть пробу
  окружения и делает почти всю работу, а камни отдавали половину. Сравнивай
  похожие объекты между собой: **если два одинаковых по смыслу объекта имеют
  разные константы — это не баланс, это забывчивость.**
- **Мерь объект, а не область экрана.** Средняя яркость фиксированного
  прямоугольника измеряет *размер* объекта и фон за ним: маленький тёмный
  корабль и большой тёмный камень выглядели как разные проблемы, хотя были
  одной. Разность двух кадров даёт маску самого объекта и убирает и то и другое.
- **Обнуляй состояние, оставленное конструктором, и не давай стенду двигать
  субъект.** Скорость, заданная фабрикой вдоль старого направления, рассасывается
  около секунды; ИИ уводит объект из кадра между двумя кадрами разности. Оба
  случая дали «эффекта нет» там, где эффект был, и «эффект есть» там, где его не
  было.
- **Если текст рисуется поверх произвольного фона, контраст обязан ехать вместе
  с текстом.** HUD рисуется прямо поверх сцены: на пустом космосе это нормально,
  над станцией строка становится тёмной по светлому. Замер по кадру с HUD и без
  него: средний контраст **1.74**, **97 % пикселей ниже порога 3:1**. Обводка
  глифов решает это на любом фоне; прямоугольная подложка — нет, потому что
  длинная строка выходит за её край.
- **Ищи двойную прозрачность.** Цвет с собственной альфой, который ещё раз
  умножается на альфу анимации, гасит себя дважды: `inkDim` (0.38) × рампа
  (0.35) = **0.13** — это не «приглушённая строка», это отсутствие строки.
  Складывай прозрачности в одном месте и проверяй **произведение**, а не
  множители по отдельности.
- **Проверяй состояние контекста на *второй* итерации, а не на первой.**
  `globalAlpha`, `lineWidth`, `strokeStyle` ставятся один раз и молча текут в
  следующий вызов: обводка второй строки журнала наследовала альфу первой
  (0.78 вместо 1.0). Тест на одной строке был бы зелёным.
- **Гаси выразительность, а не читаемость.** У затухающей строки должна гаснуть
  буква, но не обводка: иначе последняя строка перед исчезновением снова
  становится нечитаемой — ровно та ошибка, которую правка и устраняла.
- **Текст, который обещает поведение, — это код, и он стареет так же.**
  Подсказка на экране станции гласила «D undock», а `dock` привязан к KeyC;
  KeyD — это `rollRight`, то есть на станции она *двигает выделение вниз*.
  Вторая клавиша из той же подсказки, Escape, не была привязана вообще ни к
  чему. Подсказку написали один раз и с тех пор ни с чем не сверяли. **Связывай
  обещание с источником истины тестом:** тест читает и текст подсказки, и
  `BINDINGS`, и падает, если они разойдутся в любую сторону.
- **Список, которым управляют клавишами, обязан следовать за выделением.**
  Замер: 19 строк рынка, 724 px содержимого в 569 px окна, последняя строка на
  45 px ниже среза, и `scrollTop` после обхода всего списка оставался нулём.
  Стрелками можно было выбрать товар и не увидеть его. Проверяется обходом:
  сдвинь выделение по всем строкам и убедись, что **ни на одном шаге** оно не
  оказалось вне окна.
- **Правка комментария может сломать код.** Замена `// --- helpers ---` на
  `/** helpers ---` без закрывающего `*/` утащила в комментарий всё до конца
  файла, включая `el`, — 48 тестов упали с «el is not defined». Если после
  правки падает половина файла тестов, смотри не на логику, а на структуру.
- **Одна клавиша — одно действие.** `fire` и `launchMissile` оба несли KeyM
  (наследство оригинального Elite, где M была клавишей ракеты). Так как `fire`
  читается через `held`, а ракета через `consume`, срабатывало **и то и
  другое**: замер с захваченной целью — одно нажатие M снимало ракету (3 → 2)
  **и** выпускало трассер. `consume` отдаёт клавишу первому спросившему, поэтому
  **пересечение привязок всегда молчит**: либо одно действие не происходит, либо
  оба. Тест обходит всю таблицу и требует, чтобы каждый код принадлежал ровно
  одному действию.
- **Прежде чем объявить чужой вывод устаревшим — назови время обоих событий.**
  Остаточный контекст сессии не содержит хронологии и охотно подсовывает
  «после меня» вместо «после того, как прочитано». Одна команда снимает
  вопрос: `git log --format="%h %ad %s" --date=format:"%H:%M"`
  (или `git log -S"<строка>"` для конкретной правки).
- **Текст, обещающий поведение, — это код.** За одну сессию три случая: станция
  обещала «D undock» (D — это roll-right) и «Esc undock» (Escape не привязан
  нигде), карта — «ENTER = select» (Enter не привязан нигде). Все три написаны
  один раз и никогда ни с чем не сверялись. Выноси легенды в константы и
  проверяй их **против `BINDINGS`** — и буквы, и названные слова. И убедись, что
  такой тест **падает** на старой строке: тест, который не может упасть, — не
  тест.
- **Снимок показывает результат, а не причину.** Тёмные камни были тёмными
  из-за альбедо; тёмная станция на заголовке тёмная из-за **градиента,
  нарисованного поверх неё**. Внешне это одно и то же, и различить их можно
  только замером. Прежде чем менять то, что «плохо выглядит», спроси, что именно
  ты видишь: объект или что-то поверх него.
- **Проверяй, статичен ли ракурс.** «Неудачная композиция» заголовка оказалась
  одним кадром движущейся сцены: камера облетает станцию по кругу, проходя и
  светлую сторону, и теневую. Замер со стороны звезды дал среднюю яркость 78.6 и
  84 % пикселей выше 35 — плотное светлое тело. Ничего чинить не надо.
- **Число из единицы — в единственном числе.** Экран заголовка говорил
  «1 systems visited», экран смерти — «1 kills»: первые два предложения, которые
  читает новый командир. Один `countOf(n, noun)` вместо тернарника на каждом
  месте.
- **Провал в цепочке условий — это решение, принятое по умолчанию и никем.**
  HUD рисовался во всех режимах, кроме `title`, `dead` и `hyperspace`, поэтому
  `docked` попадал в `else` молча: **прицел висел поверх таблицы рынка**, кольцо
  сканера просвечивало через список цен (замер — 2.9 % кадра). Провал незаметно
  включает **всё новое**: любой добавленный позже режим получает полётный HUD, и
  никто этого не решает. Если режимов больше трёх — перечисли те, которые что-то
  делают, и сделай «ничего» явным ответом.
- **Мерь тот слой, о котором говоришь.** «Сколько HUD видно за экраном станции»
  по разности двух скриншотов не измеряется: игровой цикл продолжает рендерить
  сцену между снимками, и ~1 % «шума сцены» неотличим от содержимого HUD. Про
  содержимое канваса надо спрашивать сам канвас — счёт непрозрачных пикселей:
  flight 6.64 %, docked 0.00 %.
- **Инструмент, измеряющий поведение, проверяй второй стратегией.** Жадная по
  награде карьера в `economy-sim.mjs` берёт 16 зачисток и **ни одной** грузовой
  работы. Это читается двояко: «зачистки выгоднее» и «путь грузовых работ
  сломан». Различить одной колонкой нельзя — отсюда третья колонка, которая
  берёт грузовые работы первыми. Восемь доставок выполнились, значит путь
  работает и первая колонка показывает предпочтение, а не поломку.
- **Две версии стратегии подряд мерили стратегию, а не экономику.** Первая
  брала работу, как только руки свободны: набрала четыре, обслуживала одну,
  семь провалила, штрафы съели прибыль. Вторая держала позицию при активной
  зачистке **до того, как дошла до цели** — дни не тикали, корабль навсегда
  вставал не в той системе, финальный капитал 1 CR. **Инструмент врёт так же
  охотно, как стенд.**
- **Всё, что инструмент предполагает, а не считает, пиши в его шапке.** Доход с
  зачисток в симуляторе — верхняя граница самого себя: награда известна заранее,
  завершение предполагается, смерть не моделируется. Фильтр «успею ли долететь»
  считает прыжки по полному баку. Иначе следующий читатель примет границу за
  факт.
- **«Разницы не видно» — это утверждение о картинке, и проверяется оно
  картинкой.** Комментарий в `rng.js` объяснял выбор value-шума вместо
  градиентного: «визуальной разницы на планете при таком бюджете треугольников
  нет». Разница есть, и она не в бюджете: value-шум имеет ячейки, и на планете
  они читаются как шестиугольные грани — гранёный кристалл вместо мира.
  Комментарий, объясняющий выбор, устаревает так же, как код, и звучит при этом
  технически грамотно.
- **Тест может утверждать дефект как требование.** Тест «noise3 has no dead
  lattice lines» проверял свойство *value-шума*: что выборка вдоль линии решётки
  не константа. У градиентного шума она как раз константа — ноль, — и тест упал
  законно. Меняя природу вещи, перечитай тесты, которые её описывают: они
  написаны под старое поведение, а не под твоё намерение. И проверяй, не падает
  ли тест на **совпадении по построению**: тест «шум различается по зёрнам»
  сравнивал одну точку и попал ровно в центр ячейки, где два зерна дают ноль.
- **Скриншоты для README не клади в папку, которую перезаписывает прогон
  тестов.** Пять картинок README ссылались на `e2e-shots/`, а эта папка в
  `.gitignore` — на GitHub все они были бы битыми. Курированный набор живёт в
  `docs/screenshots/` и коммитится; черновики прогона остаются игнорируемыми.
- **Путь, который разрешается на одном компьютере, — это не зависимость.**
  `scripts/e2e.mjs` делал `require('D:/GitHub/node_modules/puppeteer-core')`:
  абсолютный путь, работавший только потому, что пакет лежал в **родительском**
  каталоге проекта. Локально всё было зелёным; CI упал с «Cannot find module», и
  у любого, кто клонирует репозиторий, `npm run e2e` упал бы так же.
  **Проверка «локально всё работает» не отличает зависимость от совпадения** —
  отличает её только прогон на другой машине. Объявляй пакет в `package.json` и
  импортируй по имени.
- **CI — это первая машина, которая не твоя.** Он нашёл этот дефект в первом же
  прогоне, потому что не имел ни родительского `node_modules`, ни моих путей.
  Заводи его до того, как понадобится.
- **Дублирование в списке — почти всегда дефект, даже когда у него есть
  объяснение в архитектуре.** Доска контрактов показывала взятое задание дважды:
  тусклой строкой «accepted» наверху и живой строкой «in progress» ниже.
  Объяснение было («предложения и принятые — один список с одним курсором»), но
  оно относилось к **курсору**, а не к строкам: курсор может ходить по списку, в
  котором одна строка на задание. Теперь взятые предложения отфильтрованы.
- **Сравнивай вычисленный стиль, а не впечатление от снимка.** Строка взятого
  контракта выглядела тусклее доступных — замер `getComputedStyle` дал
  одинаковый `rgb(159,232,255)` и `opacity: 1`. Взгляд сравнивал её с
  **подсвеченной выбранной** строкой выше и с тусклой подписью внутри неё.
  Три ложные тревоги за один раунд, все закрыты замером.
- **Убирая строку из списка, проверь, не осталось ли от неё проверки.**
  `activateContract` содержал `if (offer.taken) return notify('Already accepted')`
  — после фильтрации ветка стала недостижимой. Настоящая защита от двойного
  взятия живёт в `MISSIONS.accept` и от экрана не зависит.
- **Прежде чем крутить число, спроси, какой слой оно настраивает.** Фон карты
  гасил не только мир, но и HUD — потому что карта рисовалась последней. Подняв
  непрозрачность 0.86 → 0.96, я убрал просвечивание станции (27 % → 6 %) и
  сделал колонку статуса почти невидимой. Оба симптома имели **одну причину**:
  фон закрывал не тот слой. Правильная правка — порядок вызовов, а не значение.
- **Если правка одной константы улучшает одно и портит другое — ищи структурную
  причину.** Компромиссное значение между двумя симптомами закрепляет причину
  вместо того, чтобы её убрать.
- **Если тест падает не всегда — источник случайности в проверяемом коде, а не
  в тесте.** Прогон набора упал на тесте пламени, который до этого проходил;
  пять изолированных прогонов были зелёными. Причина: `patrolPoint` брал точку
  обхода через `Math.random()`. **Флейк — это не «тест капризничает»**: тест,
  падающий случайно, учит перезапускать прогон вместо того, чтобы читать вывод,
  и подрывает доверие ко всем остальным.
- **Проверяй, не нарушает ли код правило, которое проект сам записал.** В шапке
  `rng.js` стоит «never use `Math.random()` for anything the player can observe
  twice» — и ровно в этом модуле и его соседе было **четыре** таких вызова.
  Правило лежало в первой строке файла, который эти вызовы обслуживает.
- **Невоспроизводимый ИИ нельзя отлаживать.** Детерминизм нужен не ради зелёных
  прогонов: баг в поведении корабля, который нельзя повторить, нельзя и починить.
  Доказательство — заглушка, **бросающая исключение**: 600 кадров, ноль вызовов.
- **Ставя заглушку на `Math.random`, ставь её после создания сцены.** three.js
  зовёт `Math.random` в `generateUUID` для каждого нового `Object3D`; глобальная
  заглушка упадёт внутри three, а не внутри твоего кода.
- **Тест на сохранение, написанный по памяти, проверяет память автора, а не
  сохранение.** Проверка «сохранил деньги — загрузил деньги» была зелёной, пока
  `serialize` не писал **последнюю станцию стыковки**: `dockedAt` возвращался
  `null`, и командир, прошедший полгалактики, после перезагрузки и гибели
  попадал на Lave — при том что экран смерти обещает «rescued at your last
  station». Заполняй **все** поля записи отличительными значениями и сравнивай
  **все**.
- **Транзитные поля перечисляй списком, а не фильтруй шаблоном.** Шаблон вроде
  `/_max$/` неявно покрыл бы и `shieldMax`, который меняется от оборудования, —
  то есть пропустил бы ровно тот случай, ради которого аудит написан. И проверяй,
  что каждое имя из списка всё ещё существует в записи: иначе переименование поля
  оставит исключение, которое ничего не покрывает.
- **Проверка кругом должна повторять то, что делает `deserialize`.** `equip` и
  `standing` сливаются с умолчаниями намеренно, поэтому замена объекта целиком
  выглядела как потеря поля. Иначе аудит сообщает о дефектах, которых нет.
- **`createMemory` внутри `enterSystem` означала «память всегда пуста».**
  Механика, которая должна накапливаться между визитами, не может жить на
  объекте, который пересобирается на каждом визите. Спрашивай не «где удобно
  создать», а «сколько это должно жить».

- **`opacity` и `instanceColor` умножаются в РАЗНЫХ пространствах.** Самая
  дорогая ловушка рефакторинга неба. `material.opacity` применяется как
  `src.a`, и при аддитивном блендинге фрагмент **уже закодирован в sRGB** —
  то есть прозрачность умножает *отображаемое* значение. `instanceColor`
  умножает **линейный** цвет до кодирования. Поскольку sRGB нелинейна,
  `sRGB(c) * o != sRGB(c * o)`: при `o = 0.09` это расхождение в 2.7 раза
  (байт 7 против 19). Если переносишь прозрачность в instance-цвет, веди её
  через `convertLinearToSRGB()` → `multiplyScalar(o)` → `convertSRGBToLinear()`.
  См. `foldOpacity` в `sky.js`.
- **`InstancedMesh` требует `dispose()`.** Его `instanceMatrix` и
  `instanceColor` — буферы **объекта**, а не геометрии, и освобождаются
  только по событию `dispose` самого меша (`WebGLObjects.onInstancedMeshDispose`).
  `geometry.dispose()` + `material.dispose()` их не трогают. `disposeTree`
  это учитывает.
- **Проверяй и стенд тоже.** Диагностический скрипт сравнивал «старые» и
  «новые» слои неба, и в нём `group.children.slice()` копировал **все** дети
  вместо только что добавленного слоя — из-за чего сравнение 534 квадов с 520
  инстансами показывало фантомную разницу. Полдня ушло на «баг» в стенде.
- **Для недетерминированной сцены нужен контрольный прогон.** Трафик
  использует `Math.random()`, поэтому два прогона одной и той же сборки
  дают 8.4 % различающихся пикселей. Сравнение «до/после» показало 3.2 % —
  то есть рефакторинг отличается от базовой линии *меньше*, чем две
  одинаковые сборки друг от друга. Без контроля этот результат неотличим от
  регрессии.
- **Изоляция вместо «посмотреть глазами».** Чтобы доказать отсутствие
  визуальной регрессии, недостаточно скриншота: нужно отрисовать спорный
  объект отдельно, в обеих реализациях, с общей камерой и текстурой, и
  сравнить попиксельно. Только так нашлось расхождение в 2.7 раза, которое
  на глаз не видно вообще.
- **Дефект может быть в вызывающем, а не в функции.** `payFine` получала
  индекс системы и искала по нему `standing`, который ключуется фракцией;
  `decayWanted` вызывалась без индекса и молча ничего не делала. Юнит-тест,
  вызывающий функцию с *правильными* аргументами, такие ошибки не ловит по
  устройству — нужны тесты уровня точки входа.
- **Не пиши фикстуру, которой не бывает в реальности.** Тест «оплата штрафа
  повышает репутацию» создавал `standing[0]` — запись по индексу системы,
  которой у настоящего игрока не существует. Тест и баг согласились друг с
  другом, и оба были неправы.

- **Пламя сажаем на `hullTailZ`, не на константу.** Корпуса построены в
  разном локальном масштабе (Cobra хвост на z −2.4, trader на −4.2), а группа
  корабля ещё домножается на `SHIP_SCALE[kind]` (viper 12, trader 16). Общий
  офсет сопла стрелял бы из кабины на одном из корпусов. Мир в этой игре
  крупный: Viper — 113 юнитов, trader — 140. Кадрируя скриншот, отходи
  минимум на 400 юнитов, иначе камера окажется внутри корпуса.
- **Пламя ведём от угловой скорости, а не от газа.** У NPC нет троттла:
  `integrateEntity` всегда тянет скорость к `speed * nose`, и `speed` —
  константа. Производная скорости в установившемся полёте ноль. Вираж —
  единственный момент, когда вектор скорости реально меняется.
- **Тест на вираж держи игрока близко.** `steerToward` разворачивает нос к
  точке; на 40 000 юнитов это фиксированный курс, угловая скорость почти
  нулевая, и тест молча измеряет константу. Рабочая дистанция — сотни юнитов.
- **Прежде чем верить падающему тесту — проверь вход.** `cruise 0.236 ->
  banking 0.236` означало, что мерили не то, а не что эффект сломан.
- **Большая полупрозрачная фигура в кадре — это небо, а не баг.** Туманности
  — билборды `PlaneGeometry` в тысячи юнитов при `opacity ~0.07`; при
  неудачном ракурсе накрывают корабли мягкой пеленой. Проверяется скрытием
  подозреваемого объекта: фигура не исчезла — значит не он.

- **`Quaternion.slerp` не принимает плоский объект.** Читает приватные
  `_x/_y/_z/_w`; у обычного объекта там `undefined`, и результат молча
  `NaN` — без исключения. Симптом: 3D чёрный, граф сцены здоров, ошибок нет.
- **`OutputPass` обязан быть последним** в цепочке composer. Он единственный
  читает `outputColorSpace` и `toneMapping` с рендерера; без него картинка
  тёмная и пересыщенная.
- **Единицы измерения двойные.** Галактика — в мировых единицах (диск 260,
  `JUMP_REFERENCE` 36), топливо — в световых годах. Мост — `LY_PER_UNIT` и
  `toLy()` в `main.js`. Забыть конвертацию = «ни одна система недостижима».
- **Сфера столкновения и конус стыковки перекрываются** — Coriolis полый.
  Внутри посадочного коридора столкновения подавлены (`insideDockingCorridor`).
- **`vite-plugin-singlefile` + `format: 'iife'` сломан** в Vite 8. Оставлен
  ESM-вывод, `<script type="module">` постобрабатывается в классический тег
  в конце `<body>` (`classicScriptAtEndOfBody` в `vite.config.js`).
- **Небо обязано тестировать глубину.** `depthTest: false` на билбордах
  туманностей работает, пока в сцене только звёздный фон, и рисует заливку
  *поверх* станции, как только между камерой и поясом появляется объект. Небо
  всегда дальше сцены — достаточно обычного теста глубины. То же про
  `depthWrite: false` (его надо оставить) — это разные флаги.
- **Закрытые тела — `FrontSide`, открытые оболочки — `DoubleSide`.**
  `DoubleSide` на корпусе станции рисует дальнюю стенку через ближнюю,
  получается «стеклянный шар». Корабли — открытые вееры из 6–10 вершин, их
  без `DoubleSide` мигает на крене. Сторона выбирается в `hullMaterial(colour, side)`.
- **`polygonOffset` вешать на обводку, не на корпус.** Смещение корпуса назад
  на единицу глубины (чтобы обводка не z-fight'ила) на солиде в 150 единиц
  выпускает дальние рёбра сквозь ближнюю поверхность. Линии смещаются вперёд
  (`polygonOffsetUnits: -1`) — это не зависит от масштаба.
- **Ни один из этих трёх багов не ловится юнит-тестом** — все они про
  соотношение объектов в кадре. Скриншот здесь часть теста, а не украшение.
- **PBR-материал без `scene.environment` рендерится чёрным.** `MeshStandardMaterial`
  с `metalness > 0` отражает окружение; без пробы металл не отражает ничего.
  Проба — `src/sim/environment.js`, это жёсткая зависимость материалов, а не
  улучшение. Собирается в чистом JS (equirect `DataTexture`), а не через
  `PMREMGenerator`: тот требует render target и GPU-проход, которых нет в
  stranded-режиме (без WebGL) — и тогда headless-путь видел бы другие материалы.
- **Проба обязана быть `LinearSRGBColorSpace`, не sRGB.** При sRGB three
  декодирует текстуру и примерно возводит значения в квадрат — все отражения
  выходят заметно темнее задуманного (симптом: «PBR сделал всё мутным»).
- **Патч шейдера не должен объявлять имена, которые three уже объявляет.**
  `#include <begin_vertex>` вставляется *до* `project_vertex`, где three
  объявляет `vec4 mvPosition`. Своя переменная с этим именем — жёсткая ошибка
  компиляции GLSL, которую видит только браузер (e2e-проверка «zero console
