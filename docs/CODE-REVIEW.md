### Почему 5.4 оставлено

Оба пункта — про производительность, и **производительность с тех пор измерена**:
кадр симуляции стоит **0.03 мс** при бюджете 60 fps в 16.7 мс, а логика с рендером —
3.86 мс под программным растеризатором. Оптимизировать нечего, поэтому:

- **пересчёт рынка при покупке** (`findMarketRow` + `refreshStation`) — это два
  расчёта на покупку, а не на кадр. Кэш по `(system, day)` убрал бы это, но
  измерение говорит, что убирать нечего;
- **проход «нет тупиков»** в `galaxy.js` с `key.split(':')` — выполняется один раз
  при генерации галактики, и сам отчёт отмечал, что «не болит».

Записано здесь, чтобы следующий читатель не «починил» их, приняв открытую находку
за недосмотр.

## 1. Вердикт

Это **очень хороший код** — заметно выше среднего для проекта такого размера. Архитектура
дисциплинированная, комментарии объясняют *почему*, а не *что*, и почти каждое неочевидное
решение подкреплено разбором ошибки, которая к нему привела. Разделение слоёв соблюдается
буквально: `flight.js` не знает о HUD, `economy.js` не знает о three.js, и это не декларация,
а факт, проверяемый отсутствием импортов.

Главная проблема не в качестве кода, а в **интеграции**. Найдено семь реальных дефектов, и
шесть из них — это не ошибка в функции, а ошибка в её *вызове*. Функции написаны и покрыты
тестами правильно; ломается стык между слоями, а именно его юнит-тесты не видят по устройству.

Второй по значимости пункт — **производительность неба**: 534 из 684 мешей сцены (78 %
draw-call'ов) — это статичный фон, который никогда не меняется.

Третий — **`reputation.js` написан целиком, но не подключён**. Модуль на 202 строки с системой
памяти мира, влиянием репутации на цены и на враждебность патрулей: не вызывается ни одна из
этих функций.

## 2. Что сделано хорошо

Стоит зафиксировать, потому что это не комплимент, а описание инвариантов, которые нельзя ломать.

| Решение | Почему это правильно |
|---|---|
| **Логика без three.js** | `src/logic/*` — чистые функции. 355 тестов без браузера, без GL, без DOM. |
| **`flight.js` без единого импорта** | Состояние полёта — обычные литералы. Границу держит `render.js` через `toQuaternion()`. |
| **Рендерер строится всегда** | Даже в headless, где деградирует в `mode:'none'`. Поэтому e2e гоняет *настоящую* игру, а не тестовый режим. Это лучшее архитектурное решение в проекте. |
| **Один объект `session`** | Пересобирается целиком на прыжке. Прыжок — это одно присваивание, а не список полей, которые разъедутся. |
| **Детерминированный PRNG + изоляция потоков** | `buildSystemScene` тянет из одного `range`, планета берёт свой seed. Реролл звезды не сдвигает пояс. |
| **Экономика от профиля, а не от типа** | `imbalance = consumes - produces` одним числом, потом одна нелинейность. Именно это не даёт «денежной печатной машинке» на 3.7x. |
| **`passBudget` / `timeToKill` в combat.js** | Баланс боя выражен уравнением, а не набором констант. Комментарий объясняет, почему 7 выстрелов на проход — правильное число. |
| **Шаблон «shared» на материалах эффектов** | `userData.shared` защищает общий материал от `disposeTree` при прыжке. |

## 3. Дефекты

Отсортировано по влиянию на игру. Все проверены запуском, а не чтением.

### 3.1. Розыск никогда не истекает 🔴

**`src/main.js:778`** — `REP.decayWanted(player);`

Сигнатура: `decayWanted(player, systemIndex)` (`reputation.js:57`). Вызов без индекса читает
`player.wanted[undefined]` → `undefined` → `if (!w) return null`. Функция выходит на первой строке.

```
wanted после markWanted(p, 5, 6):  {"5":6}
после 5 дней вызова из main.js:    {"5":6}   <- не изменилось
после правильного decayWanted(p,5): {"5":5}
```

Модуль сам формулирует требование, которое нарушено: *«Being a fugitive should be a phase you
can outlast, not a permanent state»*. Сейчас это ровно permanent state: единственный выход —
заплатить штраф. Игрок, ставший Fugitive в 10 системах, остаётся им навсегда.

**Починка:** `REP.decayWanted(player, session.index)` — или, что честнее, пройти по всем ключам
`player.wanted`, потому что день идёт глобально, а не в одной системе.

**Теста нет.** `decayWanted` не упоминается ни в одном тесте.

### 3.2. `payFine` не снимает враждебность — ветка мертва 🔴

**`src/logic/reputation.js:105-107`**

```js
if (player.standing && player.standing[systemIndex] !== undefined) {
  player.standing[systemIndex] = Math.min(0, player.standing[systemIndex] + 20);
}
```

`standing` ключуется **идентификатором фракции**, а не индексом системы:
`{ FEDERATION, EMPIRE, ALLIANCE, INDEPENDENT }` (`player.js:168`). `player.standing[5]` всегда
`undefined`, поэтому условие ложно всегда.

Проверено: штраф 240 CR списан, `wanted` очищен, `standing.FEDERATION` остался `-40`.

Практическое следствие: комментарий обещает «bought off but still shot at» — и именно это и
происходит. Вы платите, запись чистится, а патруль по-прежнему настроен враждебно, потому что
`standing` не тронут.

**Починка:** нужен маппинг система → фракция: `player.standing[system.faction]`. Функция должна
принимать систему, а не индекс.

### 3.3. Docking Computer за 2500 CR не делает ничего 🔴

**`src/logic/player.js:51`**

```js
{ id: 'dock', name: 'Docking Computer', price: 2500, once: true,
  desc: 'Docks the ship for you when aligned with the slot. Removes the hardest part of flying.' }
```

`hasEquipment(player, 'dock')` не встречается **нигде** в игровом коде. Проверка:

```
=== каждое упоминание 'dock' как id предмета ===
src/logic/player.js:51:    id: 'dock', ...
--- конец ---
```

Хуже того: автодок уже работает **для всех и бесплатно** — `main.js:1845`:

```js
const v = session.dockingVerdict;
if (v && v.ok && session.grace <= 0) { dock(); return; }
```

Это второй по цене предмет в игре (после Beam Laser) и он — чистая потеря денег. Игрок покупает
его, ожидая облегчения стыковки, и не получает ничего.

**Два варианта починки, и выбор здесь содержательный:**
- **(a)** Сделать автодок платным: без компьютера стыковка требует ручного `C` и реального
  попадания в створ; с компьютером — как сейчас, автоматически. Тогда предмет продаёт
  *снятие сложности*, как и написано в описании.
- **(b)** Оставить автодок всем, но дать компьютеру другое: расширенный радиус захвата
  (`maxOffset` 46 → 80), допуск по углу и автоматическое выравнивание в створе.

Вариант (a) честнее по отношению к оригиналу, где стыковка была главным навыком, но он
**меняет баланс сложности** и требует решения владельца проекта. Вариант (b) безопаснее.

### 3.4. Границы прыжка считаются в разных единицах 🔴

**`src/main.js:439`**

```js
for (const n of GALAXY.neighbors(galaxy, session.system, session.jumpRange())) {
```

`session.jumpRange()` возвращает `player.fuel` — **световые годы** (7). `GALAXY.neighbors`
сравнивает с `GALAXY.distance()`, которая возвращает **сырые мировые единицы** (25–35 между
соседями; `DISC_RADIUS = 260`).

```
сырая дистанция   мин 1.4   макс 505.4
в световых годах  мин 0.3   макс  98.3
LY_PER_UNIT = 0.1944

neighbors(system0, fuel=7)            -> 1 система    <- так вызывают
neighbors(system0, 7 ly как единицы)  -> 6 систем     <- так задумано
маршрутами связано с system0          -> 7 систем
```

Документация `galaxy.js:374` сама вводит в заблуждение: `/** Euclidean distance in light years. */`
— но функция возвращает сырые единицы, а конвертация живёт в `main.js:toLy()`.

Сейчас баг **замаскирован**: `chartState` объединяет результат `neighbors()` со вторым проходом
по маршрутам, и те 7 систем, что даёт граф, визуально закрывают дыру. Но подсветка «достижимо
сейчас» на карте неверна, и любое будущее использование `neighbors()` унаследует ошибку.

**Починка:** `GALAXY.neighbors(galaxy, session.system, session.jumpRange() / LY_PER_UNIT)`,
плюс исправить docstring `distance()` на «in raw world units».

### 3.5. `prune()` течёт геометрией 🟠

**`src/sim/world.js:665`**

```js
if (d > LAYOUT.despawnDistance) {
  scene.remove(s.mesh);
  ships.splice(i, 1);
}
```

Ни `disposeTree`, ни `geometry.dispose()`. Сравните с `onEntityDestroyed` (`main.js:898`), где
утилизация есть — то есть автор знал о необходимости, но в ветке деспавна пропустил.

`makeShip()` создаёт **свежую геометрию на каждый корабль** (`makeCobra` → `new THREE.BufferGeometry()`),
плюс `edgeLines` и `makeFlame` добавляют ещё. Замерено: **769 уникальных геометрий и 254
уникальных материала** в сцене.

Трафик пересобирается каждые 6 секунд, корабли деспавнятся за `despawnDistance = 2600`. За
длинную сессию в одной системе это устойчивая утечка. При прыжке `commitJumpScene` её подчищает,
поэтому проблема не видна в коротком тесте — но в долгом полёте без прыжков растёт.

**Починка:** `disposeTree(s.mesh)` перед `scene.remove`. Три строки.

### 3.6. База стоимости груза теряется при загрузке 🟠

**`src/main.js:378, 541-545`**

`session.avgPaid` — стоимость закупки, по которой маркет подсвечивает выгодную продажу
(`station.js:210-211`). Две проблемы:

## 4. Мёртвый код

Не опасно, но искажает картину для следующего читателя. Особенно пункты 4.1–4.3: они выглядят
как работающие системы.

### 4.1. Система памяти мира написана и не подключена 🟠

`reputation.js` экспортирует полноценный слой событий. Проверка «кто вызывает»:

| Функция | Вызовов вне модуля |
|---|---|
| `rememberEvent` | **0** |
| `memoryDangerDelta` | **0** |
| `memoryTrafficDelta` | **0** |
| `memoryPriceDelta` | **0** |
| `patrolHostile` | **0** |
| `standingPriceFactor` | **0** |
| `STANDING_TIERS[].greeting` | **0** |
| `conditionHeadline` | **0** |

`createMemory()` вызывается ровно один раз — `main.js:279`, и результат используется только для
`rumourFor()`. Причём вызывается **внутри `enterSystem`**, то есть создаётся заново при каждом
входе в систему. Память всегда пустая, даже если бы `rememberEvent` где-то вызывался.

Итог: `standing` копится (`adjustStanding` вызывается из `onPlayerHit` / `onEntityDestroyed`),
отображается в статусе станции — и **не влияет ни на что**. `standingPriceFactor(60) = 0.94`
(скидка 6 %), но эта функция не вызывается ни разу. Репутация — чистая декорация.

Это самая крупная упущенная возможность в проекте. См. §6.2.

### 4.2. LOD объявлен и не реализован 🟡

**`src/sim/world.js:624-625`**

```js
// Deferred update: a ship far away costs almost nothing.
lod: 0,
```

`.lod` не читается нигде в `src/`. Комментарий описывает оптимизацию, которой нет:
`stepTraffic` прогоняет полное наведение и интегрирование для **каждого** корабля каждый кадр.
При `trafficTarget = 7` + 4 за опасность это ~11 кораблей — терпимо, поэтому не болит. Но
комментарий врёт.

### 4.3. `session.chartTarget` только читается 🟡

**`src/main.js:900`** — `if (entity === session.chartTarget) session.chartTarget = null;`

Поле не присваивается нигде. Условие всегда ложно. Строка безвредна, но это остаток от
нереализованной фичи.

### 4.5. Заглушки `void`

`void speed` (`main.js:1487`), `void spec` (`1637`), `void time; void accumulator` (`1748`),

Это способ заглушить линтер для неиспользуемых параметров. Но `accumulator` (`1711`) не
используется вообще нигде, а `update(time, dt)` не использует `time` — фиксированный шаг не
реализован, и `accumulator` остался от него. Лучше удалить переменную, чем глушить её.

### 4.6. `player.hold` — рудимент 🟡

Не читается **нигде**: `holdMaxOf()` выводит вместимость из `equip.cargoExt`. Поле в формате
сохранения, которое ничего не значит.

### 4.7. Неиспользуемый экспорт `MODE`

## 5. Производительность

### 5.1. Небо — 78 % draw-call'ов на статичный фон 🔴

Замерено в собранной игре:

```
мешей в сцене          684
из них небо            534      (14 туманностей + 520 пылинок)
уникальных материалов  254
уникальных геометрий   769
```

**`src/sim/sky.js:272`** и **`:290`** создают по отдельному `THREE.Mesh` со **своей**
`PlaneGeometry` на каждую туманность и каждую пылинку:

```js
for (let i = 0; i < SKY.dustCount; i += 1) {
  const quad = new THREE.Mesh(new THREE.PlaneGeometry(scale, scale), dustMat);
```

520 отдельных мешей, каждый — отдельный draw call, все прозрачные и аддитивные, поэтому
батчинг движок применить не может. При этом небо **детерминировано и бесконечно далеко**: оно
не меняется ни при каких обстоятельствах.

Документация `sky.js:19` утверждает *«Cost is deliberately tiny: three draw calls for the entire
sky»*. Фактически их 535.

**Решения, по возрастанию качества:**

1. **`InstancedMesh`** для пыли (1 материал, 1 геометрия, 1 draw call) и отдельный для
   туманностей. Быстро внедряется, сохраняет текущий вид, убирает 533 draw call'а. Требует
   переписать циклы размещения — они уже пишут матрицы, так что работа механическая.
2. **Запечь небо в кубемапу один раз при загрузке** и поставить `scene.background`. Радикально:
   535 draw call'ов → 0 (фон рисуется одним блитом). Небо всё равно никогда не меняется
   относительно наблюдателя. Минус — теряется возможность менять небо в рантайме, которой
   сейчас никто не пользуется.
3. Комбинация: кубемапа как фон + оставить звёзды (`Points`, 1 draw call) поверх для параллакса.

**Рекомендую (1)** — минимальный риск, механическое изменение, и оно оставляет небо управляемым.

Отдельно: 254 уникальных материала. Каждая туманность получает свой (`sky.js:264` — *«A fresh
material per nebula»*), и это осознанное решение ради индивидуального цвета и прозрачности.
После перехода на `InstancedMesh` это схлопнется естественным образом.

### 5.2. Выхлоп аллоцирует меш на каждую частицу 🟠

**`src/main.js:1227`** — `const mesh = new THREE.Mesh(EXHAUST.geometry, EXHAUST.material);`

`EXHAUST.rate = 90` частиц/сек, `life = 0.42` → в установившемся режиме ~38 живых мешей.
Каждая частица — это `new THREE.Mesh` + `scene.add` + через 0.42 с `scene.remove`. Итого
**~90 аллокаций и ~180 операций с графом сцены в секунду**, непрерывно, пока держишь газ.

Замерено: дети сцены 26 → 47 после прогрева и дальше стабильно 47. То есть **утечки нет**,
число ограничено. Но это крупнейший источник аллокаций в игре и постоянная нагрузка на GC.

**Решение:** один `THREE.Points` с `BufferGeometry` на N частиц и пул индексов — или
`InstancedMesh` с обновлением матриц. Частицы всё равно одного размера и цвета, различаются
только позиция и масштаб. Это убирает 90 аллокаций/сек и 180 операций с графом.

То же самое касается обломков (`spawnDebris`, 9 мешей на взрыв) — но там частота на два порядка
ниже, и трогать не обязательно.

### 5.3. Аллокации в кадре

| Место | Что | Частота |
|---|---|---|
| `render.js:347-348` | `new THREE.Vector3()` × 2 в `placeCamera` | 120/сек |
| `main.js:2055` | `new THREE.Color(t.colour)` в `drawTracers` | на трассер в кадре |

В `placeCamera` уже есть скретч-вектор `rig._tmp` и `rig._quat` — то есть паттерн в файле
принят, просто для `fwd`/`up` его не применили. Правка на две строки: добавить `_fwd`, `_up`
в `rig` и использовать их.

`drawTracers` считает `new THREE.Color` каждый кадр для каждого трассера, хотя цвет приходит
из фиксированной палитры `LASERS` (2 значения). Достаточно кэша по значению.

### 5.4. Прочее

- **`world.js:296-307`** — проход «нет тупиков»: для каждой из 64 систем перебирает **все**
  ключи `links` и делает `key.split(':')`. Это ~64 × 200 = 12 800 разборов строк. Выполняется
  один раз при генерации галактики, поэтому не болит, но карта степеней считается тривиально.
- **`main.js:619`** — `findMarketRow` вызывает `marketRows(player.day)`, то есть **пересчитывает
  весь рынок** (19 товаров, каждый с несколькими `noise1`/`hash2`) ради поиска одной строки.
  Затем `refreshStation()` строит рынок ещё раз. Покупка одной позиции = два полных пересчёта.
  Кэш по `(system, day)` убрал бы это.

## 8. Идеи: интерфейс

### 8.1. Частичная покупка и продажа 🔴 *самое нужное*

**`station.js:238-249`** — `doBuy` всегда берёт `Math.min(free, stock, afford)`, то есть максимум.
**`station.js:441`** — `activate()` на удерживаемом товаре продаёт **всё** (`row.held`).

Следствия:
- Нельзя купить 3 тонны, чтобы остались деньги на топливо и ремонт.
- Нельзя продать часть груза, оставив остаток под лучшую цену в другой системе.
- **Нельзя выпутаться из ситуации «полный трюм + пустой бак + нет денег»**, продав ровно
  столько, сколько нужно на топливо.

В оригинале покупка шла по одной тонне за нажатие — грубо, но это давало точный контроль.

**Решение:** `Shift`+`Enter` = ±1 тонна, `Enter` = максимум. Одна строка в `activate()`,
одна в `doBuy()`, подсказка в `renderHint()`. Инфраструктура уже готова: `actions.buy(id, n)`
и `actions.sell(id, n)` принимают количество.

### 8.2. Вектор скорости, а не число 🟠

HUD показывает `speed` числом (`hud.js` → `drawIdent`) и полосу `throttle`. Ни то, ни другое не
отвечает на вопрос «куда я лечу». В не-ньютоновской модели `flight.js` это важно: корабль
скользит, и вектор скорости расходится с носом.

**Решение:** маркер «prograde» (куда летишь) и «retrograde» (обратный) на визире, как в
KSP/Elite Dangerous. Считается из `flight.vel` проекцией на `forward/up/right` — данные уже
есть в `hudState`. Даёт мгновенное понимание скольжения, не добавляя ни одной новой системы.

### 8.3. Направление урона 🟠

Сейчас при попадании сзади — только текстовая строка `'Under fire from behind'` (`main.js:1356`),
и только если `dot < -0.2`. При попадании спереди или сбоку — ничего, кроме вспышки.

**Решение:** дуга-индикатор по краю экрана в направлении стрелявшего. `onEnemyShot` уже считает
`toShooter` и `dot` — осталось передать вектор в `hudState` и нарисовать. Одна новая функция в
`hud.js`. Резко снижает ощущение «меня убивают непонятно откуда».

### 8.4. Разрядка в левой колонке 🟡

Открытая проблема №2 в `CONTEXT.md`: `HOLD 0/20` и `PULSE LASER` разделены 17 px при шрифте 13 px
— запас 4 px. При `h = 1080` строки идут с шагом 17 px (`main.js` → `drawIdent`, `y + 34` и `y + 51`).

**Решение:** вынести `MSL`-пипсы в отдельную строку с шагом 20 px, либо перенести оружие и
ракеты в правый нижний угол, где сейчас пусто. Правая колонка под статус-барами свободна.

### 8.5. Карта: подсказка о топливе 🟡

Карта красит системы по опасности (`hud.js:566-570`) и рисует связи с затуханием по длине.
Но **не показывает, куда реально хватит топлива**. Игрок должен сопоставлять число `fuel` с
длиной ребра на глаз.

**Решение:** обвести достижимые системы пунктиром или приглушить недостижимые. `chartState`
уже вычисляет `jumpRange`; в `hud.js` есть `r.distance` для каждого маршрута. Нужен один
проход по системам.

Заодно исправить баг 3.4 — тогда `neighbour`-подсветка начнёт работать по назначению.

### 8.6. Мелкое

- **`main.js:1711`** — `accumulator` объявлен и не используется. Либо реализовать фиксированный
  шаг физики (полезно: сейчас `dt` плавает до 0.1 с, и при 20 fps управление ощутимо иначе),
  либо удалить.
- **`drawTracers`** — `new THREE.Color` в кадре, см. §5.3.
- **Тосты станции** (`station.js:452`) живут 1800 мс фиксировано. Для «Bought 12 t of Food for
  38.4 CR» этого мало, для «No stock» — много. Стоит масштабировать по длине текста.

## 9. Идеи: геймплей

### 9.1. Подключить репутацию 🔴 *самая крупная упущенная возможность*

Модуль готов, лежит без дела (§4.1). Минимальная связка, дающая максимум эффекта:

| Функция | Куда подключить | Что получит игрок |
|---|---|---|
| `standingPriceFactor` | `main.js:marketRows` — умножить `buyPrice`/`sellPrice` | Репутация начинает влиять на экономику: с Trusted закупка на 4 % дешевле. Сейчас обещание «trusted commanders buy cheaper» (`reputation.js:35`) — пустая строка. |
| `STANDING_TIERS[].greeting` | `enterSystem` — вместо общего `'Arrived: X'` | Прибытие в дружественную систему отличается от прибытия в Hunted. Восемь написанных реплик заработают. |
| `patrolHostile` | `createTraffic` / `enterSystem` — поднять `aggression` у `viper` | Hunted означает, что на входе встречают огнём, а не текстом. |
| `rememberEvent` + `memoryPriceDelta` | `onEntityDestroyed` пишет, `computeMarket` читает | Убил пиратов — система стала безопаснее и дешевле. Мир начинает помнить. |
| `memoryTrafficDelta` | `topUp` — скорректировать `cap` | Расчищенная система привлекает торговцев, разорённая — нет. |

Порядок: сначала первые три (дёшево, заметно сразу), потом память мира — она требует, чтобы
`createMemory()` перестала создаваться заново и была привязана к системе и сохранению.

### 9.2. Миссии и контракты 🟠

Их нет вообще (проверено). Весь геймплей — торговля и охота за головами. Это ровно то, что
`galaxy.js:6-17` называет недостатком оригинала, и здесь он повторяется.

Материал уже есть и лежит рядом:

- `F.condition(system.condition)` — условия мира: голод, блокада, бум. **Идеальный генератор
  миссий.** «Голодающей системе нужно 20 т еды» пишется в одну функцию.
- `player.standing` и `REP` — репутация как условие выдачи («дадут только Trusted»).
- `REP.conditionHeadline` — готовая строка описания.
- `system.profile.lacking` — система сама знает, чего ей не хватает.

**Минимальная версия:** на экране станции вкладка «Contracts» с 2–3 предложениями вида
«доставить N тонн товара X в систему Y за Z CR и срок D». Успех → деньги + standing, провал →
standing вниз. Доставка проверяется при стыковке. Это ~150 строк и превращает торговлю из
«купил дёшево, продал дорого» в осмысленный маршрут.

### 9.3. Скимминг топлива у звезды 🟡

Сейчас звезда — чистый фон на 9000 единиц, и `Fuel Scoops` обещает то, чего нет (§3.8).

**Решение:** сделать звезду достижимой (или добавить отдельную «близкую» точку скимминга),
и давать топливо пропорционально близости к фотосфере, с ростом тепла. Это:
- оправдывает описание предмета;
- даёт альтернативу заправке за деньги — то есть реальный выбор;
- задействует `HEAT`, который сейчас работает только как лимитер лазера;
- создаёт риск: близко подошёл — перегрелся.

Сейчас `HEAT` тикает вниз всегда, а тепло идёт только от выстрелов. Механика расширяется без
новых систем.

### 9.4. Реализовать LOD или убрать комментарий 🟡

`entity.lod` объявлен, комментарий обещает отложенное обновление, которого нет (§4.2). При 11
кораблях это не проблема, но `stepTraffic` считает полное наведение и интеграцию для всех,
включая тех, кто в 2500 юнитах и не виден.

**Решение:** пропускать `steerToward`/`integrateEntity` для кораблей дальше `despawnDistance * 0.8`,
обновляя их раз в N кадров. Комментарий тогда станет правдой.

### 9.5. Docking Computer — решить, чем он является

См. §3.3. Сейчас это 2500 CR в пустоту. Это не мелочь: предмет в списке, у него есть цена и
описание, и он не работает. Либо вариант (a), либо (b).

### 9.6. Экономический баланс на длинной дистанции 🟡

Открытая проблема №3 в `CONTEXT.md` и она подтверждается чтением: `driftFactor` даёт ±11 %
(`economy.js:158`), обратная тяга к базе — 15 % (`economy.js:198`). Обе константы разумны по
отдельности. Но **калибровки на 50+ прыжках не было**, а `player.activity` ускоряет рынок
(`marketDay = day + floor(activity * 0.15)`), то есть активный игрок видит другую экономику,
чем измеряли в тестах.

**Решение:** прогнать headless-симуляцию «100 прыжков, оптимальный арбитраж» и посмотреть
кривую капитала. Если она экспоненциальная — поднять `activity`-множитель. Инфраструктура
для этого есть: логика чистая, `node --test` уже так работает.

## 10. Идеи: окружение

### 10.1. InstancedMesh для неба 🔴

См. §5.1 — это одновременно и производительность, и качество. После перехода можно **поднять**

### 10.2. Один источник света — добавить второй 🟡

Сейчас свет один: `sunLight` от звезды (`world.js:541`). Плюс `planetLight` и `cockpitLight`.

Но отсюда следует и другое: **у корабля нет затенённой стороны, читаемой как объём**. PBR-отклик
на пробу окружения даёт блики, но не даёт направленного контраста. Второй слабый источник
(отражение от планеты, если планета близко) дал бы корпусам «нижнюю» подсветку и заодно
создал бы приёмник для теней, если они когда-нибудь понадобятся.

### 10.3. Планета: оживить поверхность 🟠

`makePlanet` (world.js:211) и `PLANET_PALETTES` (world.js:383) — сейчас это сфера с процедурной
раскраской и, судя по открытой проблеме, «блобовые» облака.

Что можно добавить, не нарушая «один файл, ноль ассетов»:
- **Терминатор.** Резкая граница дня и ночи с подсветкой атмосферы по краю на дневной стороне.
  Сейчас освещение ровное; линия терминатора мгновенно читается как «это планета, а не шар».
- **Города на ночной стороне.** Несколько точек-огней там, где ночь. Прямо связывается с
  `system.population` — плотность огней становится визуализацией населения.
- **Кольца** для части систем: дёшево (один annulus), а силуэт системы меняется радикально.

### 10.4. Астероидный пояс: разнообразие 🟡

Открытая проблема №6: *«у астероидов нет вариативности формы сверх деформации октаэдра»*.

**Решение:** второй и третий примитив (`DodecahedronGeometry`, `IcosahedronGeometry`) с той же
деформацией, выбор по seed. Плюс лёгкий разброс цвета материала — сейчас все 90 камней одного
цвета, что и делает пояс однообразным сильнее, чем форма. Пять строк, заметный эффект.

### 10.5. Мусор как след деятельности 🟡

Мир статичен: пояс, станция, планета, звезда — и всё. Нет признаков, что здесь кто-то живёт.

**Решение:** обломки у станции (сбитые корабли, `dropCargo` уже умеет создавать канистры),
дрейфующие контейнеры на торговых маршрутах, обломки у пояса. `dropCargo` и `spawnDebris`
существуют; нужно лишь расставить их в `buildSystemScene` детерминированно от seed. Даёт:
- визуальный интерес в пустоте;
- бесплатную награду исследователю (дрейфующий контейнер = находка);
- ощущение, что система живёт независимо от игрока.

Согласуется с `REP.createMemory` (обломки = след прошлых событий) — если репутацию подключить
(§9.1), это свяжется в одну историю.

### 10.6. Ориентация на станции 🟡

Стыковка требует попасть в створ (`maxOffset = 46`, `maxAngle = 0.42`). Створ — на вращающемся
корпусе (`spinRate` 0.22–0.34 рад/с). Это хорошая сложность.

Но игрок не видит, **куда именно** нужно попасть, пока не подлетит: `drawDockingGuide` включается
на FLIGHT, но нет дальнего маркера створа. В оригинале была «docking computer»-подсказка и
отдельный визир.

**Решение:** на HUD — маркер створа (маленькая скоба на корпусе станции) с расстоянием, видимый
с 2000 единиц. `insideDockingCorridor` и `arrivalPose` уже знают геометрию створа
(`station.userData.slotNormalLocal` / `slotPointLocal`) — данные для проекции есть.

### 10.7. Звук: двигатель и окружение

`audio.js` — 355 строк процедурного синтеза, 30 тестов. `setEngine(throttle, boost)` вызывается
из `update()`.

Что можно добавить дёшево:
- **Доплер** для пролетающих кораблей: `stepTraffic` знает относительную скорость.
- **Гул станции**, нарастающий при приближении, — станция вращается, у неё есть масса.
- **Скрежет при столкновении** — `checkCollisions` знает силу удара, но играет только `hitHull`.

## 12. Итог

Код заслуживает того, чтобы его дорабатывать, а не переписывать. Слои разделены честно,
комментарии объясняют решения, тесты проверяют инварианты. Найденные дефекты — это не
небрежность, а **цена дисциплины**: раз логика вынесена в чистые модули с собственными тестами,
ошибка переезжает на стык, где тесты её не видят. Именно поэтому все семь багов — в вызовах,
а не в функциях.

Три вещи стоит держать в голове:

1. **Три модуля без собственных тестов — `reputation.js`, `player.js`, `factions.js` — и в двух
   из них найдены баги.** Это не совпадение. `reputation.js` при этом содержит самую интересную
   неиспользованную механику проекта.
2. **Небо — 78 % draw-call'ов.** Это единственная серьёзная техническая проблема, и она
   решается одним `InstancedMesh`.
3. **Частичная покупка — самая дешёвая правка с самым заметным влиянием на игру.** Одна строка
   в `activate()`, одна в `doBuy()`.

Ничего из перечисленного не требует переписывания архитектуры. Это признак того, что она верная.
