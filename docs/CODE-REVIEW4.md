## Резюме

Это **сильный** код. Разделение `logic / sim / ui / core`, чистые функции,
seeded RNG, отсутствие циклических зависимостей, 694 юнит-теста и headless
e2e через `file://` — уровень, который встречается редко. Комментарии объясняют
причины решений, а не пересказывают код, и это не поза: найденные ниже дефекты
почти все — остатки прошлых правок, а не архитектурные провалы.

Но ревью жёсткое, поэтому главное:

1. **Один настоящий баг с последствием для игрока:** моргание огней посадочного
   слота — мёртвая анимация (`.intensity` пишется в `MeshBasicMaterial`).
   Тест это «проверяет» и проходит, потому что проверяет поле, а не картинку.
2. **Два мёртвых пути управления:** `limits.range` в `checkDocking` недостижим
   (и вместе с ним недостижим весь смысл дальности в `DOCKING.assist`), а
   сообщение о повышении ранга в `decayDay` не может сработать.
3. **Ключевое число «на глаз»:** 5 строк статус-баров захардкожены в `drawIdent`
   числом `5`. Добавление шестой строки молча ломает раскладку.
4. **Тесты, которые читают исходник регуляркой, а не поведение** (9 мест).
   Это не тесты — это дубликат текста, который придётся чинить при каждом
   рефакторинге, а ломает он неверно: зелёный тест ничего не доказывает.

Ниже — по существу.

## Классификация

- **[баг]** — некорректное поведение, видимое игроку или ломающее механику.
- **[мёртвый код]** — недостижимый путь, неиспользуемое поле, мёртвый экспорт.
- **[хрупкость]** — работает сейчас, сломается при осмысленной правке рядом.

## 1. Мёртвый код и недостижимые пути

### 1.1 Моргание огней посадочного слота не работает — [баг]

`world.js`, `spinStation` пишет `b.intensity` в элементы `station.userData.beacons`.
Эти элементы созданы в `models.js`, `makeCoriolis`, как `THREE.Mesh` с
`THREE.MeshBasicMaterial`. У `MeshBasicMaterial` нет свойства `intensity` —
оно есть у `Material` только в смысле пользовательского поля, но рендер его
не читает. Присвоение молча уходит «в никуда»: огни **горят ровно и не мигают**.

Подтверждено: `tests/geometry.test.js` («the station has blinking beacon lights»)
проверяет только `b.isMesh` и позицию по Z, а `tests/world.test.js`
(«beacons blink over time») читает `st.userData.beacons[0].intensity` — то есть
то самое поле, которое записано, но не влияет на изображение. **Оба теста
зелёные при полностью мёртвой анимации.** Это худший вид зелёного теста:
он закрепляет ровно то поле, из-за которого баг и существует.

Комментарий над кодом («Blink phase comes from an accumulated clock…») описывает
намерение честно и подробно — и именно поэтому расхождение с реальностью
обиднее: задумано верно, сделано мимо.

Починка — не в этом ревью (правки запрещены), но она однострочная: моргать
надо `material.color` (через `setScalar`/умножение) или `material.opacity`,
либо перейти на `MeshStandardMaterial`/`SpriteMaterial`, где `intensity`
осмыслен только при аддитивном режиме.

### 1.2 `limits.range` в `checkDocking` недостижим — [мёртвый код] + [баг]

`world.js`, `checkDocking`: строка

```
const inside = d < R0 * 1.6;            // R0 = stationRadius = 150 → порог 240
...
if (!inside) return ... 'out-of-range';  // d >= 240 → выход
if (speed > limits.maxSpeed) ...
if (lateral > limits.maxOffset) ...
if (angle > limits.maxAngle) ...
if (d > DOCKING.clearance && d > limits.range) return ... 'out-of-range';
```

Проверка `limits.range` (260 в стоке, **460** с компьютером) стоит **после**
`if (!inside)`, а `inside` — это `d < 240`. То есть до неё доходит только
`d < 240`, где `d > 460` заведомо ложно, а `d > 260` тоже ложно для всех
`d < 240`. **Условие всегда false.** Ветка мертва целиком.

Следствие: заявленная «дальность 460 у компьютера» не влияет ни на что.
`dockingLimits(true)` возвращает `range: 460`, тест
«dockingLimits gives the computer a strictly wider envelope» проверяет
`assisted.range > stock.range` — и это правда про объект конфигурации и ложь
про поведение. Дальность читается `checkDocking`, но не проверяется.

Почему тесты не ловят: `approachAt` в `tests/world.test.js` ставит корабль на
`40` вдоль оси слота и `offset` поперёк. Для «sloppy approach» это
`sqrt(40² + 95²) ≈ 103` — глубоко внутри 240. Ни один тест не подводит корабль
в диапазон `240..460`, именно тот, где разница стока и компьютера и живёт.
Тест «the computer still refuses an approach from across the system» бьёт
по `x = 6000`, что отсекается тем же `!inside`, а не `range`.

Итого: механика «компьютер расширяет дальность» существует в конфиге,
в комментарии и в тесте на конфиг — и не существует в игре.

### 1.3 Сообщение о повышении ранга в `decayDay` мертво — [мёртвый код]

`main.js`, `decayDay`:

```
const before = PLAYER.rankOf(player.kills);
if (!silent && before !== PLAYER.rankOf(player.kills)) {
  say('Rank: ' + ...);
}
```

`player.kills` в этой функции не меняется — меняются день, offences, wanted.
Значит `before === PLAYER.rankOf(player.kills)` тождественно, ветка `say` не
выполняется никогда. Реальные сообщения о ранге живут в `onEntityDestroyed` —
там, где киллы и начисляются. Здесь остался труп от прошлой попытки.

Это безвредный труп (не ломает поведение), но он врёт читателю: выглядит как
действующая фича.

### 1.4 `state.mouse` — поле, в которое только пишут ноль — [мёртвый код]

`input.js`: поле `state.mouse = { x: 0, y: 0 }` создаётся, и далее **все четыре**
обращения к нему — обнуление (`releaseStick`, `endFrame`, `releaseMouse`).
Живой путь — `state.mouseTarget`, его читает `stepMouse`, он же затухает в
`stepMouse` и он же возвращается из `stickFrom`-цепочки.

То есть `state.mouse` неотличимо от мёртвой копии `mouseTarget`. Либо это
остаток старой схемы «мышь как позиция» (до перехода на virtual-stick), либо
заготовка. В любом случае — удалять; сейчас он только сбивает того, кто
будет читать `stepMouse`.

### 1.5 `message` в `createStationUI` не используется — [мёртвый код]

`station.js`: `const message = el('div', 'elite-sub');` создаётся и **никогда**
не добавляется в DOM и не читается (проверено: `message` встречается в файле
ровно один раз — в объявлении). Соседние `hint` и `toast` добавлены в `root`.
Либо элемент потеряли при рефакторинге, либо это осколок. Удалить.

### 1.6 `raycast` возвращает `normal`, которого никто не читает — [мёртвый код]

`world.js`, `raycast`: в результат кладётся `normal: { x: -nx, y: -ny, z: -nz }`.
Проверено: `hit.normal` в `src/main.js` не читается нигде (единственный
потребитель `raycast` — `fireLaser`, и он использует `hit.point` и `hit.target`).

Хуже, чем мёртвое поле: **значение неверное**. `{-nx,-ny,-nz}` — это
обратный вектор луча, а не нормаль поверхности в точке попадания. Нормаль сферы
в точке — `(point - centre)/|…|`. Сейчас это совпадает с обратным лучом только
при строго центральном попадании. Пока поле не читается — безвредно; но
первый же, кто им воспользуется (рикошет, декали, звук по нормали), получит
мусор.

### 1.7 Мёртвый экспорт `timeToKill` — [мёртвый код]

`combat.js`: `timeToKill` экспортируется и попадает в `default`-зеркало.
Вызовов нет ни в `src/`, ни в `tests/`, ни в `scripts/` (проверено grep по
всем трём деревьям). Сосед `passBudget` — используется (`tests/combat.test.js`),
`timeToKill` — нет. Держится только тем, что его имя упомянуто в комментарии
над `passBudget`.

Отдельно: `FIRE_RANGE` в том же файле не используется в самом файле, но
используется в `world.js` — это нормальный экспорт, не трогать.

## 2. Хрупкость

### 2.1 Жёсткая `5` в `drawIdent` — мина под раскладкой — [хрупкость]

`hud.js`, `drawIdent`:

```
const y = h * 0.06
  + 5 * (HUD_LAYOUT.barHeight * k + ...) + 6 * k;
```

`5` — это длина массива `rows` в `drawStatusBars` (SHLD, FUEL, ENRG, HEAT, HULL).
Число продублировано в двух функциях без связи. Добавьте шестую строку
(например, `CARG` или `SPEC`) — бары удлинятся, а идентификация не сдвинется,
и цифры наложатся на полосы. Молча.

Правильно — экспортировать `STATUS_ROWS` (или хотя бы длину) из одного места
и считать обе позиции от неё. Сейчас между `drawStatusBars` и `drawIdent`
есть невидимый контракт, которого нет в коде.

### 2.2 `DOCKING.clearance` vs `inside` — два порога, один из них ложь — [хрупкость]

Рядом с 1.2 живёт третье число: `clearance = 62` («inside this, you are
committed») с комментарием, обещающим смысл, которого нет — `checkDocking`
не ветвится по `clearance` ни в одном достижимом пути (`d > DOCKING.clearance`
входит в уже мёртвое условие). Комментарий активен, поведение — нет.
Три числа (`R0 * 1.6`, `clearance`, `limits.range`) описывают «насколько
близко надо быть», и ни одно из них не является настоящей границей:
настоящая — `R0 * 1.6 = 240`, невыразимое, нигде не названное явно.

### 2.3 `drawChartOverlay` → `info.population.toFixed(1)` — [хрупкость]

`hud.js`: `info.population.toFixed(1)` без проверки на `undefined`. Все прочие
поля рядом защищены (`state.laser || 'pulse'`, `state.cash || 0`, `cap > 0`).
Здесь — нет. Если в `chartState` (main.js) однажды не окажется `population`
(новый тип строки, тайник, что угодно) — HUD падает с `TypeError` в середине
кадра, то есть чёрный экран поверх игры. Проверить, что `population` всегда
кладётся, и либо оставить, либо защитить.

### 2.4 `drawIdent` уходит за край на узком экране — [хрупкость]

`drawIdent` складывает до четырёх строк ниже баров (`MSL` + pips + `+N`),
считая от `h * 0.06`. На низком окне (widescreen-ноутбук, `h < 480`) суммарная
высота баров + идентификации может вылезти за низ. `hudScale` масштабирует,
но не перекладывает. Не проверял на реальном окне — помечаю как подозрение,
а не факт.

### 2.5 Тесты, читающие исходник регуляркой — [хрупкость]

Найдено **9** обращений к `readFileSync` в тестах; из них минимум шесть —
`assert` по тексту исходника, а не по поведению:

- `tests/station.test.js` — «STORED STATION CSS defines the classes the code
  uses»: регуляркой `classList\.(add|toggle|remove)\('([a-z-]+)'` выскребает
  имена классов и проверяет, что CSS содержит `.` + имя. Это тест на
  форматирование исходника: перепишите `classList.toggle('a-' + x)` — тест
  позеленеет, ничего не проверив; а переименуйте класс — упадёт не тот тест.
- `tests/hud.test.js` — «the launch prompt is visible for most of its blink
  cycle»: регулярка требует буквально `const blink = Math.sin(session.time * 3) > <число>;`.
  Любая правка выражения (хоть вынос частоты в константу) уронит тест,
  хотя поведение не изменится.
- `tests/hud.test.js` — «the title screen scales its text»: режет исходник по
  `indexOf('function drawTitle')`, что сломается при переименовании или
  перестановке функций.
- `tests/render.test.js` — три теста: один режет `drawTitle` по
  `indexOf`, другие — по `match(/new THREE\.AmbientLight\(…/)` и по
  `match(/toQuaternion\(flight\.quat\)/g)`.

Это **не доказательство поведения**. Такой тест ломается при безобидном
рефакторинге (ложная тревога) и проходит при реальной поломке (ложное
спокойствие), если правильный литерал остался рядом. Авторы честно пишут в
комментариях, что «reads the source rather than a built scene, which is the
honest place to assert a tuning constant» — но честное место для *числа*
(`AmbientLight(0x…, 0.32)`) — экспортируемая константа, а не текст файла.
Пока число в литерале, тест проверяет не константу, а её запись.

Инструмент, который увидeл бы настоящую проблему: тест поведения +
экспортируемая константа. Это системный долг, а не огрех отдельного теста.

### 2.6 `dropCargo` сидируется только по `position.x` — [хрупкость]

`world.js`, `dropCargo`:

```
const rand = R.mulberry32((seed ^ Math.floor(position.x * 1000)) >>> 0);
```

В сид идёт только X. Два разных корабля, взорванных на одном X (например, в
одной струе обломков, или один на `(100, 0, 0)`, другой на `(100, 0, 5000)`),
получат **одинаковый** разлёт канистр и одинаковый спин. Сосед `dropCapsule`
сделан аккуратно — там в сид идёт `position.z` (тоже одна ось, та же проблема,
но другая). Согласованности нет: один по X, другой по Z.

Симптом игрока: кластеры канистр из разных киллов иногда выглядят клонами.
Не ахти какая беда, но это ровно тот случай, где «сид + соль по позиции»
применён наполовину.

### 2.7 `makeAsteroid` / `rockTypeFor`: сид 0 и сид 1 неразличимы — [хрупкость]

`models.js`: `R.mulberry32((seed >>> 0) || 1)`. `seed === 0` (или `(seed>>>0) === 0`)
подменяется на `1`, поэтому два *разных* сида — `0` и `1` — дают идентичную
форму камня. То же в `rockTypeFor`. Это защита от нулевого сида в mulberry32,
но она строит коллизию ровно в точке, где сиды должны различаться.
В генераторе пояса (`seed` от `GALAXY_SEED`, обычно nonzero) это не стреляет;
но публичная функция `makeAsteroid(0)` и `makeAsteroid(1)` — один и тот же
камень, а тесты (`tests/geometry.test.js`) проверяют разные сиды вразнобой и
уже однажды могли случайно пройти. Мина под тестом, не баг в игре.

### 3.3 `scannerRanges` объявлен `let`, но не меняется — [долг]

чтение. `let` намекает на мутабельность и заставляет вернуться и проверить.
`const`. Мелочь, но таких мелочей в файле на 3316 строк — важна каждая.

### 3.4 `main.js` — 3316 строк, 92 функции — [долг]

Это самый большой файл проекта, почти в два раза крупнее следующего
(`world.js`, 1540). Внутри него лежат и boot, и state machine, и бой, и
отрисовка death/title/hyperspace, и работа с DOM-панелями. Функции мелкие и
чистые — это его спасает, — но навигация по 3316 строкам стоит времени, а
циклических зависимостей он избегает *комментариями*, а не структурой
(см. `saveVocabulary` — почему она живёт здесь, объяснено, и объяснение верное).

Не требую дробить сейчас: дробление без нужды — это изменение ради изменения.
Но если появится пятая система (ещё один шар состояния, ещё одна панель),
файл надо будет резать — и делать это сейчас дешевле, чем через тысячу строк.

### 3.5 Разные соглашения о сидировании в пределах одной функции-семейства — [долг]

См. 2.6: `dropCargo` солит по X, `dropCapsule` — по Z. Это симптом того, что
нет одного хелпера «сид из точки». Одна строка:

```
function pointSeed(position, seed) { … hash всех трёх осей … }
```

убрала бы и 2.6, и будущие повторы. Сейчас — терпимо, но это тот вид долга,
который копится незаметно.

## 4. Что проверено и признано корректным

Чтобы не создавать впечатление, что ревью искало только плохое:

- **`teardownScene` действительно не течёт.** Проверил цепочку
  `teardownScene → traffic.dispose() → disposeTree(root)` и то, что
  `renderer.setSystemGroup` только отсоединяет root, а также что тени и туман
  снимаются. Комментарий в `main.js` (что `setSystemGroup` «detaches the root,
  it does not free it») соответствует коду. Тесты `dispose.test.js` и
  `render.test.js` покрывают контракт `userData.shared`.
- **Seeded RNG выдержан.** `Math.random` встречается только там, где
  повторяемость не нужна игроку: шум аудио (`audio.js`), шум тряски камеры
  (`render.js`), эффекты взрыва/обломков (`main.js`), и как fallback в
  `stepTraffic` и `dust.js`. Ни один из них не влияет на то, что игрок может
  наблюдать дважды. Есть даже тест «nothing in the traffic simulation reaches
  for Math.random».
- **Сохранения защищены.** `loadGame` через `deserializeChecked` +
  `saveVocabulary` отвергает сейв с нечисловым `cash` или `currentSystem` за
  границей таблицы, и падение чтения не бьёт игру. Лучше, чем нужно.
- **Экономика не печатает деньги множителями.** `profileFactor` сознательно
  сворачивает «производит/потребляет/условие/дрейф» в один imbalance ради
  сохранения шкалы, и комментарий объясняет, почему (иначе «3.7x — это не
  рынок, а денежный станок»). Модель, которая это ломает, здесь не найдена.
- **`696`-тестовый корпус + e2e через `file://`** — сильная сторона проекта.
  Проблема не в количестве, а в том, что часть тестов (2.5) проверяет текст,
  а не поведение; и в том, что тест на моргание (1.1) закрепляет баг.
